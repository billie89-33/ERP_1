# Authentication & Role-Based Access Control (RBAC)

ระบบความปลอดภัยของ ERP เราจะใช้ **JWT (JSON Web Token)** ร่วมกับ **HttpOnly Cookie** ซึ่งเป็นมาตรฐานความปลอดภัยสูงสุดระดับ Enterprise ป้องกันการถูกแฮ็กขโมย Token (XSS Attack) ได้ดีกว่าการเก็บลง `localStorage` ครับ

## 🔐 1. ระบบ Authentication (การยืนยันตัวตนด้วย JWT + Cookie)

คำถามที่ว่า "ใช้ jwt cookie parser ได้ไหม?" 
**ตอบ:** ได้แน่นอนครับ! แต่ใน C# .NET Core เราไม่ต้องลงไลบรารีเพิ่มเหมือน Node.js เพราะ Microsoft มีระบบจัดการ Cookie และ JWT มาให้ในตัวเลยครับ

### Flow การทำงาน (Login Process)
1. **[Angular]** ส่ง Username + Password ยิง API ไปที่ `/api/auth/login`
2. **[C# API]** ตรวจสอบรหัสผ่านใน Database
3. **[C# API]** ถ้าถูกต้อง จะสร้าง **JWT String** ขึ้นมา (ข้างใน JWT จะฝัง `UserId` และ `Role` ไว้)
4. **[C# API]** แทนที่จะส่ง JWT กลับไปเป็นข้อความ C# จะจับ JWT ยัดใส่ลงใน **`HttpOnly Cookie`** แล้วแนบไปกับ HTTP Response
5. **[Angular]** ได้รับ Cookie แต่โค้ด Angular จะ "อ่าน Cookie นี้ไม่ได้" (เพื่อความปลอดภัย) 
6. **[Angular]** เวลาจะยิง API ดึงข้อมูลครั้งต่อไป Angular แค่เปิดโหมด `withCredentials: true` บราวเซอร์จะแอบส่ง Cookie ตัวนี้กลับไปหา C# ให้เองโดยอัตโนมัติ!

## 👥 2. ระบบ Roles & Authorization (การกำหนดสิทธิ์)

เราจะแบ่ง Role ออกเป็น 3 ระดับหลักๆ ดังนี้ครับ:

### 👑 1. Admin (ผู้ดูแลระบบ)
*   **สิทธิ์:** ทำได้ทุกอย่างในระบบ
*   **หน้าจอ (Angular):** เห็นทุกเมนู
*   **API (C#):** เข้าถึงได้ทุก Endpoint

### 💼 2. Sales (ฝ่ายขาย B2B)
*   **สิทธิ์:** เน้นระบบขาออก (เอาเงินเข้าบริษัท)
*   **หน้าจอ (Angular):** เห็นเมนู ลูกค้า, ใบเสนอราคา (Quotation), บิลขาย (Sales Order) และดูสต๊อกสินค้าได้ (แต่แก้ไขสต๊อกไม่ได้)
*   **API (C#):** อนุญาตให้ยิง API สร้าง SO/Quotation ได้ แต่ถ้าแอบยิง API สร้าง PO จัดซื้อ ระบบจะเตะออก (403 Forbidden)

### 📦 3. Purchasing (ฝ่ายจัดซื้อและคลังสินค้า)
*   **สิทธิ์:** เน้นระบบขาเข้า (เอาของเข้าบริษัท)
*   **หน้าจอ (Angular):** เห็นเมนู ซัพพลายเออร์, ใบสั่งซื้อ (Purchase Order), หน้าจอรับของเข้าสต๊อก
*   **API (C#):** อนุญาตให้ยิง API เพิ่มสต๊อก และสร้าง PO ได้ แต่ดูบิลขายลูกค้าไม่ได้

## 🚧 การป้องกัน 2 ชั้น (Double Protection)

การทำ ERP ห้ามป้องกันแค่หน้าบ้านเด็ดขาด เราต้องป้องกัน 2 ชั้นครับ:

1. **ป้องกันหน้าบ้าน (Angular Route Guards):** 
   เราจะเขียน `RoleGuard` ดักไว้ที่ Router เช่น ถ้าพนักงาน Role `Sales` แอบพิมพ์ URL `/purchase-orders` บนบราวเซอร์ Angular จะดีดกลับไปหน้า Dashboard ทันที
2. **ป้องกันหลังบ้าน (C# [Authorize] Attribute):**
   สมมติพนักงานเขียนโค้ดแฮ็ก ทะลุหน้าบ้านมาได้ แล้วพยายามยิง API ตรงๆ เข้ามาที่ C# 
   เราจะใส่โค้ด `[Authorize(Roles = "Purchasing, Admin")]` ดักไว้บนหัว API จัดซื้อ พอ C# แกะ JWT ออกมาดูแล้วพบว่าเป็น Role `Sales` ระบบ C# จะปฏิเสธการทำงาน (Return 403) ทันทีครับ!

## 📸 3. ระบบรักษาความปลอดภัยในการอัปโหลดรูปภาพ (Unsigned Uploads)

เพื่อความรวดเร็วในการทำงาน (ลดภาระ C# Backend) เราตั้งค่า **Cloudinary** ให้เปิดรับการอัปโหลดรูปแบบ **Unsigned (ไม่ต้องลงนาม)** ผ่านรหัสลับ (Upload Preset) เช่น `erp_upload`

**ความเสี่ยง:** หากมีคนรู้รหัส `erp_upload` เขาจะสามารถอัปโหลดไฟล์ขยะเข้า Cloudinary ของเราได้
**วิธีแก้ปัญหาด้วยระดับ Database (RBAC):**
แม้ว่ารูปภาพจะลอยเข้าไปใน Cloudinary ได้อย่างอิสระ แต่ **"URL ของรูปภาพนั้น จะไม่มีวันถูกบันทึกลงในระบบ ERP ได้ ถ้าไม่ใช่ Role ที่กำหนด"** 

เราจะจำกัดสิทธิ์ **Master Data Management (การจัดการสินค้าและรูปภาพ)** ไว้ดังนี้:
*   **✅ Admin:** สร้างสินค้าใหม่, แก้ไข, และบันทึก URL รูปภาพลง Database ได้
*   **✅ Purchasing (จัดซื้อ):** สร้างสินค้า/อุปกรณ์ไอทีใหม่ๆ และบันทึก URL รูปภาพลง Database ได้
*   **❌ Sales (ฝ่ายขาย):** มองเห็นสินค้าและรูปภาพได้อย่างเดียว ไม่มีสิทธิ์ยิง API บันทึกรูปภาพใหม่ลงตาราง Products

ดังนั้น หากมีแฮกเกอร์อัปโหลดรูป "แมว" เข้า Cloudinary เขาจะไม่สามารถดึง URL รูปแมวนั้นมายัดใส่ฐานข้อมูลเราได้ เพราะ C# Backend จะเตะออก (403 Forbidden) ทำให้รูปแมวนั้นกลายเป็นแค่ไฟล์ขยะ (Orphaned file) ที่ไม่กระทบกับหน้าร้าน ERP ของเราครับ
